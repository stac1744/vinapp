MR·STAC Diagnostics v2.1

Oct 5, 2026Owner @FredRepo stac1744/vinappStatus Draft for sign-off

Every car MR·STAC buys gets scanned at pickup, and the scan adjusts the offer. v2.1 keeps that goal. It adds a scored method for choosing which improvements ship to www.mrstac.com and in what order, and it re-plans the build around what the current codebase actually contains.

Gate · fix before any feature work

The vinapp repo contains malware

The initial commit (a9f7b0d) added files under data/ that match a common IoT botnet dropper: .update (a stripped 64-bit Linux executable), arm7.kok (an ARM executable), eight more *.kok files for other CPU types, and .monitor, a shell loop that relaunches a deleted binary every 60 seconds. sync.log shows the repo was copied from a live server at /var/www/vinapp, so that server should be treated as compromised.

  • Take the /var/www/vinapp host offline and rebuild it from a clean image. Do not clean it in place.
  • Rotate every credential that host could read: n8n webhook URLs and keys, database, SSH, hosting, and DNS.
  • Remove data/.update, data/.monitor, every data/*.kok file, and the empty stray files in the repo root. Consider purging them from git history as well.
  • Turn type and lint checks back on (next.config.js currently ignores build errors) and add a CI check that fails on any committed executable.

What changed from v2

New Phase S

Two weeks to secure and clean up the repo and server. Nothing ships until it's done.

Platform reality

vinapp has no database, login or API of its own. Every route forwards to n8n webhooks, so Phase 0 now builds that foundation.

Selection method

Each candidate is scored on value, reach, ease, unlocks and risk. The score decides whether it is a must-have, stretch or deferred item.

Quick wins added

VIN decode with open recalls, a "known codes" field on the lead form, and detection of codes cleared before pickup.

Moved later

Engine audio, publishing to listings, and Mode 06 drop from must-have to stretch or deferred, based on their scores.

Fixed contradiction

The battery-drain mitigation needs voltage gating, which v2 put in Phase 3. It now ships with the scanner in Phase 1.

How improvements are selected

Each candidate gets a 1–5 rating on five factors. The technician advisor and product owner rate them together at kickoff, and again at each phase sign-off as new data arrives.

Score = 3·Value + 2·Reach + 2·Ease + 1·Unlocks − 2·Risk (max 38)

Value

Improves offer accuracy or margin per car, or prevents a loss.

Reach

Share of leads, pickups or site visitors it touches.

Ease

5 means under one developer-week; 1 means more than four.

Unlocks

How many other candidates depend on it.

Risk

Technical, legal or seller-trust exposure.

Decision rules

  1. Gates come first. Security fixes and license compliance aren't scored. They block everything else until they're done.
  2. Score 24 or higher makes an item a must-have in the earliest phase its dependencies allow.
  3. Score 18–23 makes it a stretch item. It ships only if the phase's must-haves pass their demo with capacity left.
  4. Below 18 it goes to the backlog and gets re-scored at the next phase sign-off.
  5. Capacity cap: a phase's must-haves can't exceed 80% of its developer-weeks. The rest absorbs adapter and field surprises.
  6. Out of scope stays cut unless the product owner reopens it in writing.

Scope by phase

Each phase ships only when its must-haves pass a demo on real yard vehicles. Phase S runs in parallel with Phase 0, but no new endpoint goes live until Phase S is signed off.

S · SecureWeeks 1–21–1.5 dev-wks

Rebuild the compromised host, rotate secrets, purge malware and stray files, turn on type and lint checks, and add CI that blocks binaries and runs the build.

Done when: a clean host serves the site, and CI fails on a test commit that adds an executable.

0 · FoundationWeeks 1–44–5.5 dev-wks

Add Postgres, token login, /api/v1 with a minimum-app-version check, shared validation schemas, and direct-to-storage uploads. Import OBDex and Wal33D codes and build /codes. Add VIN decode with open recalls and a known-codes field to the lead form.

Done when: any code returns its meaning, causes and repair estimate in under 500 ms, and a lead with a VIN shows the decoded vehicle and its open recalls.

1 · ScannerWeeks 4–129.5–12.5 dev-wks

Bluetooth Classic connection with robust adapter startup. Reads VIN; stored, pending and permanent codes; readiness with an "inspection ready" verdict; and battery voltage. Recent-clear detection. Voltage-gated polling with a 5-minute limit when the engine is off. Offline upload that never creates duplicates. Clearing codes is for technicians only.

Done when: results match a reference scan tool on 10 test cars, a scan uploads in 3 minutes or less, and a car cleared the same morning gets flagged.

2 · ReportWeeks 11–186–8 dev-wks

Condition report on the seller status page, with a PDF built by a background job. Guided photos. A rules engine that proposes offer changes with reasons, which an agent approves. Stretch: Mode 06 catalyst results feeding the catalyst quote, and publishing reports to listings.

Done when: agents approve scan-based offer changes from the queue, and reports render on a phone.

3 · CoverageWeeks 17–245–7 dev-wks

Re-score the backlog first. Likely picks: BLE adapters, multi-ECU access with OBDb profiles, and engine audio. The yard and shop subscription stays on hold until pricing is set.

Done when: the phase's re-scored must-haves pass their demo. For multi-ECU, that means reading transmission and ABS data on three or more makes.

With two developers the plan runs 24 weeks, two more than v2 because of Phase S and the foundation work. Drivers start scanning real pickups at week 12. With one developer, expect 36–40 weeks.

Components and licenses

Unchanged from v2. Use only Apache-2.0, MIT and CC0 material in the product, and confirm each license in its repo before merging: kotlin-obd-api, ETSoftwareStudio/obd-scanner-android, barnhill/AndroidOBD, tronikos/elm327_obdii, OBDex and the Wal33D dtc-database. OBDb profiles are CC BY-SA 4.0, so attribute them and share edited profiles back. Do not copy AndrOBD, ELM327-emulator or WiCAN profiles. NHTSA data is public domain.
